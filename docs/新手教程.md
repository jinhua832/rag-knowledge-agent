## 0. 先看清楚：这个项目到底做了什么

一句话：**把你自己的文档变成"可被提问"的知识库，让大模型看着你的资料回答，并且告诉你答案出自哪一段。**

用户看到的三栏界面：

```
┌──────────────┬─────────────────────────┬──────────────┐
│ 知识库管理    │        对话区            │   检索片段    │
│              │                         │              │
│ · API接入指南 │  你：去北京出差住宿标准？  │ [1] 员工手册  │
│ · 员工手册    │  AI：一线城市 500 元/晚  │     3.1 差旅… │
│ · 产品FAQ     │      以内 [1]           │     相似度 70%│
│ · 入职指南    │                         │ [2] 入职指南  │
│              │  来源：员工手册 > 3.1    │     七、福利…  │
└──────────────┴─────────────────────────┴──────────────┘
```

数据流（记住这张图，后面每一章都在填其中的一块）：

```
文档 → 切分(chunk) → 向量化(embedding) → 存进 Chroma
                                              ↑
用户提问 → 向量化 → 相似度检索 top_k ← ─ ─ ─ ─ ┘
                      ↓
        拼成「带编号的参考资料」塞进 Prompt
                      ↓
                  大模型生成
                      ↓
        回答里出现 [1][2] → 前端右侧对应高亮
```

**为什么值得做这个项目**：它是少数"看起来简单、做起来全是坑"的项目。切分切坏了、检索召回不准、Prompt 没约束住、流式接口被 nginx 缓冲、引用编号对不上……每一个坑都能在面试里聊 10 分钟，而"只会调 API"的人答不上来。

**你能得到什么**：一个可运行的仓库 + 一套可复现的评测方法 + 一段能讲清楚的工程经历。

## 1. RAG 原理：5 分钟搞懂

### 1.1 一个类比

大模型是一个**知识渊博但没见过你公司内部文件**的实习生。

- **直接提问** = 让他闭卷考试。他不会就说不会，但也可能为了面子瞎编。
- **RAG** = 允许他开卷：先把可能相关的几页资料找出来放在他面前，让他"只根据这几页"作答，并标出引用页码。

开卷考试要做三件事，对应 RAG 的三个环节：

| 环节 | 干什么 | 本项目对应 |
| --- | --- | --- |
| 建库 | 把文档切成小块，每块算一个"语义指纹"（向量） | `loader.py` + `embedder.py` + `vectorstore.py` |
| 检索 | 用问题的向量去比对，找出最像的几块 | `vectorstore.search()` |
| 生成 | 把这几块原文塞进 Prompt，让模型基于它们回答 | `chain.py` + `prompts.py` |

### 1.2 为什么用「向量」而不是「关键词搜索」

关键词搜索匹配的是**字面**："年假几天" 搜不到写着"带薪休假天数"的段落。
向量搜索匹配的是**语义**：两句话意思接近，向量距离就小。中文用 `bge` 系列效果很好。

代价是：它对"精确编号""代码片段"不敏感（问"错误码 429 是什么"可能召回不准），所以进阶方案是向量 + 关键词混合检索。

### 1.3 三个必须知道的坑

1. **切分决定上限**：一段话被切断了上下文，模型看到的就是半句话，再强的模型也答不准。
2. **Prompt 决定下限**：不明确要求"只依据资料 + 标注编号"，模型一定会掺自己的记忆。
3. **检索错 = 全错**：召回的是错文档，模型越听话错得越离谱。这也是为什么要有第 11 章的评测。

### 5.1 放文档

`backend/data/docs/` 里已经放了 4 份虚构公司文档，方便你直接跑：

| 文件 | 内容 |
| --- | --- |
| 员工手册.md | 考勤、年假、报销、加班调休、保密 |
| 星尘笔记产品FAQ.md | 价格、存储、功能、退款 |
| API接入指南.md | 鉴权、限流、错误码、接口列表 |
| 新员工入职指南.md | 入职流程、账号、设备、试用期 |

**换成你自己的资料**：把 `.md` / `.txt` / `.pdf` 丢进这个目录，删掉示例文件即可。建议先放 3～10 份、总量几万字，效果最直观。

### 5.2 跑建库

```bash

```

实际输出（我这台机器跑的）：

```

向量库目录：/…/backend/chroma_db
Embedding：api / BAAI/bge-m3
切分参数：chunk_size=400, overlap=80
------------------------------------------------------------
建库完成：4 个文档，47 个片段

检索测试：入职满3年有几天年假

[1] 相似度 0.751 | 员工手册.md · 星尘科技员工手册（2026 版） > 二、假期制度 > 2.1 年假
    年假按累计工龄计算，入职当年按剩余月份折算： | 累计工龄 | 年假天数 | …
[2] 相似度 0.674 | 员工手册.md · … > 2.3 婚假、产假与陪产假
[3] 相似度 0.671 | 新员工入职指南.md · 一、入职前准备
[4] 相似度 0.670 | 员工手册.md · … > 2.4 事假
```

**怎么读这个输出**：

- `47 个片段`：4 份文档被切成 47 小块。
- `相似度 0.751`：越接近 1 越像。0.75 对中文短问题已经算"很准"。
- `员工手册.md · 二、假期制度 > 2.1 年假`：这是**引用可回溯**的关键——每块都带着章节路径。

### 5.3 这一步的代码在讲什么

**切分**（`app/rag/loader.py`）。三个细节决定了检索质量：

```python
# 1) Markdown 先按标题切，顺便把标题记进 metadata
md_splitter = MarkdownHeaderTextSplitter(
    headers_to_split_on=[("#", "h1"), ("##", "h2"), ("###", "h3")],
    strip_headers=False,
)
# 2) 再按长度细切，中文必须加这些分隔符
splitter = RecursiveCharacterTextSplitter(
    chunk_size=400, chunk_overlap=80,
    separators=["\n\n", "\n", "。", "！", "？", "；", "，", " ", ""],
    keep_separator=True,
)
```

- 为什么按 `。！？` 切：默认分隔符是英文的 `\n\n`/空格，中文长段落会从句子中间劈开。
- 为什么留 `overlap=80`：让相邻两块有一段重叠，避免答案正好被切在边界上。
- 为什么记章节：`section` 会一路带到前端，用户看到的是"《员工手册》· 2.1 年假"，而不是"某个 md 的第 3 块"。

**参数怎么定**（`CHUNK_SIZE` / `CHUNK_OVERLAP`）：

| 场景 | 建议 | 原因 |
| --- | --- | --- |
| 制度、FAQ、手册 | 300～500 字，overlap 20% | 一段一个知识点，检索更准 |
| 技术文档、论文 | 600～1000 字 | 上下文依赖强，太碎会看不懂 |
| 全是表格 | 把表整块保留 | 表格切开就废了 |

**改完参数必须 `--rebuild` 全量重建**，否则新旧片段的切法不一致，检索结果会变得很奇怪。

### 5.4 验收标准

1. 输出里有 `建库完成：N 个文档，M 个片段`，M ≥ 文档数；
2. 用一句**你自己文档里的话**去搜，第一条结果的相似度 > 0.6，且内容确实相关。

> 这一步不过关就别往下走。检索不准，后面接多强的模型都没用。

如果这里报 401 / 没 key，去配 `.env`；如果答得很空、只说"没有找到"，说明检索没命中，回头做第 5 步。

### 6.2 核心代码：三步拼成一条链

`app/rag/chain.py` 里，真正"编排"的部分就这几行：

```python
prompt = ChatPromptTemplate.from_messages([
    ("system", prompts.ANSWER_SYSTEM_PROMPT),
    MessagesPlaceholder("history"),                    # 多轮历史（可为空）
    ("human", "【参考资料】\n{context}\n\n【用户问题】\n{question}"),
])
chain = prompt | self.llm | StrOutputParser()          # ← LangChain 的管道语法
```

`|` 就是"上一步的输出喂给下一步"。这个 chain 的输入是 `{"context": ..., "question": ..., "history": [...]}`，输出是字符串。

### 6.3 Prompt 为什么这么写

`app/rag/prompts.py` 里的 system prompt，每一条都是踩过坑之后加的：

```text
1. 只依据【参考资料】里的内容作答。不要使用你自己的通用知识，也不要根据文件名猜测内容。
2. 每一处结论后面紧跟引用编号，格式为 [1]、[2]，编号只能来自【参考资料】。
3. 资料不足以回答时，直接说明「知识库里没有找到相关内容」……
4. 如果多份资料互相矛盾，要明确指出矛盾之处，并分别标注编号……
5. 用简体中文回答，结论先行……
```

- 第 1 条不写，模型会把训练记忆掺进来（"一般公司年假 5 天"）。
- 第 2 条不写，你永远不知道哪句话是编的。
- 第 3 条最关键：**给它一条体面的退路**，它就不编了。实测不写这条，"CEO 是谁"这种问题它会答出一个虚构的人名。
- 第 4 条是给真实场景留的：公司文档多了以后，两版制度并存很常见。

参考资料拼装（`prompts.format_context`）会把编号和来源写死：

```text
[1] 来源：《员工手册.md》 · 星尘科技员工手册（2026 版） > 三、报销制度 > 3.1 差旅报销标准
| 一线城市住宿 | 500 元/晚以内（北京、上海、深圳、广州） | …

[2] 来源：《新员工入职指南.md》 · 七、福利概览
- 午餐补贴 25 元/天 …
```

编号顺序 = 前端卡片顺序，这样 `[1]` 点过去才对得上。

```bash
"
```

你会看到：RAG 能给出"68 元/年"并带 `[1]`；直接提问要么说不知道，要么编一个价格。**这就是你要写进 README 的那句话。**

### 7.3 用 curl 先试，别等前端

```bash
# 只测检索（最快定位"是不是检索的锅"）
# 注意：中文必须编码，直接把中文拼在 URL 里服务器会回 400 / "Invalid HTTP request"
curl -G "http://127.0.0.1:8000/api/search" --data-urlencode "q=年假有几天" --data-urlencode "k=3"

# 一次性问答
curl -X POST http://127.0.0.1:8000/api/chat/sync \
  -H "Content-Type: application/json" \
  -d '{"question":"入职满3年有几天年假？","session_id":"t1"}'

# 流式（-N 关掉 curl 缓冲，否则你会以为它卡住了）
curl -N -X POST http://127.0.0.1:8000/api/chat \
  -H "Content-Type: application/json" \
  -d '{"question":"去北京出差住宿标准是多少？","session_id":"t2"}'
```

流式返回长这样（`event:` 行 + `data:` 行 + 空行）：

```
event: meta
data: {"sources":[{...},{...}],"standalone_question":"去北京出差住宿标准是多少？","use_rag":true}

event: token
data: {"text":"一线城市"}

event: token
data: {"text":"住宿 500 元/晚以内"}

event: done
data: {"answer":"…","latency_ms":646,"cited_ids":[1]}
```

**为什么先推 `meta` 再推 token**：右侧的检索结果不用等模型写完就能展示，用户能立刻看到"它找到了什么"，等待感大幅下降。这是产品细节，面试可以讲。

### 7.4 SSE 在服务端怎么写

```python
def event_stream():
    for ev in service.stream(question, history, top_k, use_rag):
        yield f"event: {ev['event']}\ndata: {json.dumps(ev['data'], ensure_ascii=False)}\n\n"
        if ev["event"] == "done":
            sessions.append(session_id, question, ev["data"]["answer"])

return StreamingResponse(
    event_stream(),
    media_type="text/event-stream",
    headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"},
)
```

- `\n\n` 是 SSE 的分隔符，少一个换行前端就解析不出来。
- `X-Accel-Buffering: no` 是给 nginx 看的：不关掉它，nginx 会攒够一整包才发，流式直接变"一次性"。
- `ensure_ascii=False`：不然中文会变成 `\u5e74\u5047`，虽然前端能解，但调试时看不懂。

### 7.5 验收标准

`/docs` 里四个接口都是绿的，`/api/chat/sync` 返回的 JSON 里 `answer`、`sources`、`cited_ids` 都有值。

| --- | --- | --- |

### 8.3 这三个地方最容易写错

**(1) 不能用 `EventSource`。** 它只支持 GET，而我们要 POST 传问题体。所以用 `fetch` + `ReadableStream` 自己解析：

```js
const reader = res.body.getReader();
const decoder = new TextDecoder();
let buffer = "";

while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  buffer += decoder.decode(value, { stream: true });

  const blocks = buffer.split("\n\n");
  buffer = blocks.pop();            // ★ 最后一段可能是不完整的，留到下一轮

  for (const block of blocks) {
    let event = "message", data = "";
    for (const line of block.split("\n")) {
      if (line.startsWith("event:")) event = line.slice(6).trim();
      else if (line.startsWith("data:")) data += line.slice(5).trim();
    }
    if (data) handlers.onEvent(event, JSON.parse(data));
  }
}
```

`buffer.pop()` 这一行是必写项。不写的话，一个 JSON 被两个网络包从中间切开，`JSON.parse` 就会炸——而且只在网络慢的时候炸，最难查。

**(2) 引用编号要对得上。** 后端给片段编了 `1,2,3…`，前端按键值找卡片：

```jsx
const cite = part.match(/^\[(\d+)\]$/);
if (cite) {
  const id = Number(cite[1]);
  const exists = sources.some(s => s.id === id);   // 越界编号不渲染成按钮
  ...
}
```

后端 `cited_ids()` 已经把不存在的编号过滤掉了（模型偶尔会写 `[7]`），前端再兜一层，避免点到空。

**(3) 消息状态要分清"流式中"和"已完成"**：

| 状态 | 界面 | 数据 |
| --- | --- | --- |
| 刚发出 | "正在检索知识库…" | `content: ""`, `streaming: true` |
| 收到 `meta` | 右侧出现 4 张卡片 | `sources: [...]` |
| 收到 `token` | 逐字追加 + 光标闪烁 | `content += text` |
| 收到 `done` | 光标消失、显示耗时/引用 | `latency`, `citedIds` |
| 出错 | 红框 + 错误信息 | `error: "..."` |

### 8.4 验收标准

2. 点回答里的 `[2]`，右侧第 2 张卡片边框变绿并滚动到视野内；
3. 生成中点"停止"，输出停住但不报错；
4. 关掉检索（左侧"对比模式"），右侧显示"当前是直接提问模式"。

## 9. 第 5 步：文档管理（上传 / 删除 / 增量索引）

这一步是"demo"和"能用的工具"的分界线。

### 9.1 上传接口做了什么

```python
@app.post("/api/documents")
async def upload_document(file: UploadFile = File(...)):
    name = Path(file.filename or "").name        # 只取文件名，防目录穿越
    if Path(name).suffix.lower() not in SUPPORTED_SUFFIXES:
        raise HTTPException(400, "只支持 .md/.txt/.pdf")
    if len(content) > 15 * 1024 * 1024:
        raise HTTPException(400, "文件超过 15MB")
    (settings.docs_dir / name).write_bytes(content)
    chunks = vectorstore.index_file(settings.docs_dir / name)
    return {"ok": True, "source": name, "chunks": chunks, **vectorstore.list_documents()}
```

三个细节：
- `Path(...).name` 防止有人传 `../../etc/passwd` 这种路径；
- 限制体积，避免一次上传吃掉内存；
- 返回**完整清单**，前端不用再发一次请求。

### 9.2 为什么重新索引前要先删

```python
def _delete_source(source: str) -> None:
    existing = store.get(where={"source": source}, include=["metadatas"])
    ids = existing.get("ids") or []
    if ids:
        store.delete(ids=ids)
```

不删的后果：同一份文件改完再传，旧片段还在库里。检索时会同时召回"旧版"和"新版"两段，模型看到矛盾内容，就会在回答里说"资料之间存在矛盾"——你会以为是模型的问题，其实是索引脏了。

### 9.3 `manifest.json` 是什么

`backend/chroma_db/manifest.json` 是给前端看的"知识库目录"，不参与检索：

```json
{
  "updated_at": "2026-11-16T14:06:51",
  "total_chunks": 47,
  "embedding": {"provider": "local", "model": "BAAI/bge-small-zh-v1.5", "chunk_size": 400},
  "documents": [
    {"source": "员工手册.md", "size": 4661, "chunks": 14, "updated_at": "..."}
  ]
}
```

为什么不直接查 Chroma？因为 `collection.get()` 在文档多了以后会变慢，而 manifest 是一次写入、直接读取。顺便它记下了**当时用的 embedding 模型和切分参数**——换模型后你能立刻发现"库里是旧模型的向量"。

### 9.4 验收标准

## 10. 第 6 步：多轮对话与指代消解

### 10.1 为什么"那它呢"检索不到

第一轮问"星尘笔记 Pro 版多少钱"，第二轮问"那它要提前几天申请？"。
如果直接拿"那它要提前几天申请？"去检索，向量里没有"它"指谁，命中率会崩。

解法：**先用模型把问题改写成独立完整的问题，再去检索**。

```python
def rewrite(self, question, history):
    if not settings.enable_rewrite or not history:
        return question                      # 第一轮不用改写，省一次调用
    out = self.rewrite_chain.invoke({"history": _to_messages(history), "question": question})
    rewritten = (out or "").strip().strip("“”\"'")
    if not rewritten or len(rewritten) > 80 or "\n" in rewritten:
        return question                      # ★ 兜底
    return rewritten
```

改写 Prompt（`prompts.REWRITE_SYSTEM_PROMPT`）：

```text
你是一个检索查询改写器。请结合【对话历史】，把用户的最新问题改写成一句可以独立拿去检索的完整问题。
- 补全省略的主语和对象，把「它」「这个」替换成历史里出现过的具体名词；
- 保留用户原本的说法和关键词，不要添加历史中没有出现的新信息；
- 只输出改写后的问题本身，不要解释、不要加引号。
```

**第 11 行那个 `len > 80` 的兜底不是摆设**。我在联调时就遇到模型不老实改写，而是开始"回答问题"，结果一段 200 字的回答被当成检索词，整轮检索全废。加了长度和多行判断之后，最差也只是退回原问题。

### 10.2 历史怎么存、怎么裁

```python
history.append({"role": "user", "content": question})
history.append({"role": "assistant", "content": answer})
history = history[-self.max_turns * 2:]      # 只留最近 N 轮
```

- 存内存（`SessionStore`），重启就清空——**单机 Demo 够用，生产要换 Redis**。
- 只留最近 4 轮（`HISTORY_TURNS=4`）：既能让"它/上面说的"有指代对象，又不至于 Prompt 无限膨胀烧 token。

### 10.3 验收标准

连着问三句：

```
你：星尘笔记 Pro 版一年多少钱？
AI：68 元/年 [1]
你：团队版呢？
AI：268 元/人/年，最少 5 人起购 [2]
你：那有折扣吗？
AI：超过 50 人可联系销售申请阶梯折扣 [2]
```

第三轮的 footer 会出现「检索词：星尘笔记团队版有折扣吗」——说明改写生效了。

## 11. 第 7 步：20 条评测，证明 RAG 真的有用

只跑通不算本事，**能量化才算**。这一章是简历上最值钱的部分。

### 11.1 测试集怎么设计

`backend/data/questions.json`，20 条，分四类：

| 类型 | 数量 | 例子 | 考察 |
| --- | --- | --- | --- |
| 单点事实 | 9 | "满 3 年有几天年假？" | 基础检索准确率 |
| 数字/条件 | 6 | "一线城市住宿上限？" "超过 7 天能退款吗？" | 是否抓住限定条件 |
| 跨文档 | 2 | 不同文档同类信息 | 会不会串档 |
| **无答案** | 3 | "股票代码？" "CEO 叫什么？" "年会几月？" | **会不会编造** |

每条都写了 `keywords`（自动判分用）和 `source`（期望来源文档）：

```json
{
  "id": 1,
  "type": "answerable",
  "question": "入职满 3 年的员工，一年有几天年假？",
  "source": "员工手册.md",
  "keywords": ["10 天", "10天"]
}
```

> `keywords` 要写"答案里必然出现的字符串"，且把"10 天/10天"这种空格变体都列上，否则模型写成"十天"你就误判成错了。

### 11.2 先只测检索（不花钱）

```bash
python -m scripts.eval --retrieval-only
```

实际输出：

```
[ 1] 检索命中 | 入职满 3 年的员工，一年有几天年假？
…
[17] 检索命中 | 新员工的试用期是几个月？
[18] 检索未命中 | 星尘科技的股票代码是多少？
[19] 检索未命中 | 星尘科技的 CEO 叫什么名字？
[20] 检索未命中 | 公司年会一般在几月举办？
```

**注意口径**：后 3 条"未命中"是**预期的**——文档里本来就没有答案，检索层不该命中。所以命中率按 17 条算。报告里我也写了这句注，别让人误读成 85%。

### 11.3 再跑完整评测（要 Key）

```bash
python -m scripts.eval
```

它会为每题跑两遍：`use_rag=True` 和 `use_rag=False`，然后判：

| 判定 | 规则 |
| --- | --- |
| 检索命中 | 期望文档出现在 top_k |
| 回答正确 | 回答里包含任一 `keywords` |
| 正确拒答 | 无答案题里包含"没有找到/没有相关/不确定"等措辞 |

报告会输出一行结论：`RAG 相比直接提问，正确率提升 X 个百分点`。**这就是你 README 里那句话的数据来源。**

### 11.4 跑出问题怎么办：迭代清单

我调这个项目时踩过的典型情况，按"先改哪个"排序：

| 现象 | 先查什么 | 怎么改 |
| --- | --- | --- |
| 期望文档完全没进 top_k | 片段内容 | 打开 CSV 看召回的是哪段；大概率切分把答案切断了 → 调小 `CHUNK_SIZE` 或加大 overlap |
| 进了 top_k 但排第 3、4 | 相似度差距 | 提高 `TOP_K` 到 6；或给片段开头补上章节标题（本项目已把 section 存进 metadata） |
| 检索对但回答编了 | Prompt | 把"资料不足就说没找到"提到第 1 条；temperature 降到 0.1～0.2 |
| 回答对但没标引用 | Prompt | 加 few-shot 示例；或在代码里强制后处理（无引用的句子打 `[?]`） |
| 无答案题也硬答 | Prompt | 补一句"资料里没有就直接说没有，不要用通用知识推测" |
| 多轮第二问跑偏 | 改写 | 看 `standalone_question` 是不是变长了；给改写加长度兜底 |

**改完一定要重跑 `--rebuild` + `--retrieval-only`**，别凭感觉"好像好一点了"。

```nginx
    proxy_buffering off;          # ★ 不关掉，流式回答会变成"一次性蹦出来"
    proxy_read_timeout 300s;
}
```

## 14. 写进简历 & 面试怎么讲

### 14.1 简历写法（在你的版本上补数据）

> **个人知识库问答 Agent（RAG）** | 个人项目 | Python / LangChain / Chroma / React
> - 独立实现检索增强全链路：Markdown 按标题切分 → 向量化 → Chroma 余弦检索 → 带编号 Prompt 拼装 → 流式生成 → 引用回溯，**20 条测试问答检索命中 17/17、Top1 17/17**；
> - 设计「对比模式」与自动化评测脚本，量化 RAG 相对直接提问的提升，并据此迭代切分粒度（400 字 / overlap 80）与 Prompt 约束；
> - 前端基于 React + SSE 实现三栏联动：回答中的 `[n]` 可点击定位原文片段，生成中支持中断；
> - 覆盖文档增量索引、同名文件去重、多轮指代改写（含异常兜底）等工程细节。

### 14.2 三个必被追问的问题

**Q1：你的 RAG 和"把文档贴进 Prompt"有什么区别？**
> 贴进去受上下文长度限制，而且每次都全量塞、成本高、噪声大。RAG 是"按需取用"：只把最相关的 4 个片段（约 1000 字）送进去，成本可控、噪声小，还能给出引用位置。文档涨到几百份时，贴法直接不可用。

**Q2：检索不准怎么办？你做了什么？**
> 先定位是"没召回"还是"排得靠后"——我写了 `--retrieval-only` 的评测脚本，能直接看每题的召回列表和相似度。没召回多半是切分问题（中文默认分隔符会从句子中间劈开，我补了 `。！？；`）；排得靠后是相似度区分度不够，可以提高 top_k、把章节标题写进 metadata、或者上混合检索 + rerank。

**Q3：怎么保证它不瞎编？**
> 三层：① Prompt 明确"只依据资料 + 资料不足就说没有"，并给出体面的拒答话术；② 强制每条结论带 `[n]` 编号，后端会校验并过滤越界编号；③ 测试集里专门放 3 条"文档里根本没有答案"的问题（股票代码、CEO 姓名、年会时间），跑评测看它是不是硬答。前两层是事前约束，第三层是事后度量。

### 14.3 讲的时候主动交代不足

面试官最烦"什么都很完美"。主动说：
- 会话历史存内存，多实例要换 Redis；
- 纯向量检索对精确编号不敏感，下一步加 BM25 混合 + bge-reranker；
- 没有鉴权，只适合内网 Demo。

**能说清边界的人，比说"都做完了"的人可信。**

## 15. 下一步能加什么

按"性价比"排序：

1. **混合检索**（BM25 + 向量，RRF 融合）：解决"错误码 429""函数名"这类精确匹配问题，代码量不大，效果立竿见影。
2. **Rerank**：召回 20 条 → bge-reranker 重排取前 4，精度提升明显，代价是多一次模型调用。
3. **引用高亮到句子**：现在定位到片段，可以进一步在前端把命中的那句标黄。
4. **评测自动化**：把 20 条扩到 50 条，加"多跳问题"（需要两段资料联合推理），接 CI 每次改 Prompt 自动跑。
5. **会话持久化 + 多知识库**：一个用户可以有多个库，按库检索。
6. **权限**：文档级权限，谁能看什么。
