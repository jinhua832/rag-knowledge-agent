## 一、评测集怎么设计

文件：`backend/data/questions.json`，共 20 条。

| 类型 | 数量 | 目的 | 举例 |
| --- | --- | --- | --- |
| 单点事实 | 9 | 基础检索准确率 | 满 3 年有几天年假？ |
| 数字 / 限定条件 | 6 | 是否抓住条件（"超过 7 天"、"一线城市"） | 一线城市住宿上限多少？ |
| 跨文档 | 2 | 会不会串档 | Token 有效期（API 文档）vs 试用期（入职文档） |
| 无答案 | 3 | **会不会编造** | 公司股票代码？CEO 姓名？年会几月？ |

每条的结构：

```json
{
  "id": 15,
  "type": "answerable",
  "question": "免费版调用 API 每分钟最多多少次？",
  "source": "API接入指南.md",
  "keywords": ["60"]
}
```

- `source`：期望命中的文档，用于判"检索命中"；
- `keywords`：答案里必然出现的字符串，用于判"回答正确"；
- `type=unanswerable`：文档里没有答案，判"是否正确拒答"。

> 设计原则：**每道题都必须能在文档里找到唯一、确定的答案**，否则没法自动判分。这也是为什么我用一份虚构公司的文档做示例——数字和流程都由我定，标准答案明确。

## 二、指标定义

| 指标 | 定义 | 为什么看它 |
| --- | --- | --- |
| 检索命中率 | 期望文档出现在 top_k 里 | 检索没命中，后面必错 |
| Top1 命中率 | 期望文档排在第 1 | 排第 4 时噪声更大，容易带偏模型 |
| 回答正确率 | 回答包含任一 `keywords` | 端到端效果 |
| 正确拒答率 | 无答案题里出现"没有找到/不确定"等措辞 | 幻觉的量化指标 |
| 检索耗时 | 单题检索耗时（不含生成） | 体验与成本 |

## 三、本机实测结果（检索层）

环境：本地向量模型 `BAAI/bge-small-zh-v1.5`，`chunk_size=400`，`overlap=80`，`top_k=4`，4 份文档切成 47 个片段。

| 指标 | 结果 |
| --- | --- |
| 检索命中率（17 条有答案的题） | **17/17 = 100%** |
| Top1 命中率 | **17/17 = 100%** |
| 平均最高相似度 | 0.667（最低 0.514） |
| 检索耗时中位数 | 36 ms |
| 冷启动首题 | 30.8 s（本地模型首次加载 + 联网校验） |

说明：
- 3 条"无答案"题在检索层标为"未命中"，这是**预期的**——库里本来就没这段内容。所以命中率按 17 条算，不是 20 条。报告里也写了这句注，避免被误读成 85%。
- 冷启动那 30.8 秒是本地向量模型首次加载造成的；第二种起请求就是几十毫秒。**如果用云端 embedding，没有这个问题**（代价是每题多一次网络往返）。

逐题明细见 [评测报告-检索.md](评测报告-检索.md)，完整 CSV 在 `backend/output/eval_result.csv`。

> **结论：RAG 相比直接提问，正确率提升 42 个百分点（7/17 → 15/17）。**

把这行数字填进 README 的「效果」表格，就是你的真实数据。

### 判分口径的局限（写进 README 才显得诚实）

- `keywords` 命中判定很粗糙：回答写"十天"而 keywords 写"10 天"就会误判。缓解办法是把常见变体都列进 keywords。
- 正确拒答靠措辞匹配，模型说"这个问题不在我的资料范围内"也会被判对，属于宽松口径。
- 只测了"能不能答对"，没测"答案是否完整、是否有用"——那需要人工打分，20 条大概 30 分钟能打完，建议自己补一列"人工评分（1-5）"。

## 五、迭代记录：我改了什么，为什么改

这部分是面试最容易被追问的，也是最能体现"你真的做过"的。

| # | 问题现象 | 根因 | 改动 | 效果 |
| --- | --- | --- | --- | --- |
| 1 | 中文段落经常被从句子中间切断，检索到的片段读起来是半句 | 默认分隔符按英文规则（`\n\n`、空格）切 | `RecursiveCharacterTextSplitter` 增加 `。！？；，` 作为分隔符，`keep_separator=True` | 片段语义完整度明显提升，检索相似度从 0.4~0.5 提升到 0.65~0.75 |
| 2 | 引用只显示"来自 员工手册.md"，用户没法核对 | 只存了文件名 | Markdown 按标题预切，把 `h1/h2/h3` 拼成 `section` 写进 metadata | 前端显示"《员工手册》· 二、假期制度 > 2.1 年假"，可直接定位 |
| 3 | 多轮第二问"那它呢"检索全跑偏 | 代词没有指代对象 | 加查询改写（LLM 把问题补全） | 多轮追问命中率恢复 |
| 4 | 改写偶尔"不老实"：模型开始直接作答，200 字回答被当成检索词 | 改写 Prompt 约束不足 + 无兜底 | 改写结果加 `len ≤ 80` 且不含换行才采用，否则回退原问题 | 最差退回原问题，不会整轮崩掉 |
| 5 | 同一份文档改完再传，检索会同时召回新旧两版，模型说"资料矛盾" | 只 `add` 没 `delete` | 索引前先按 `source` 删旧片段 | 内容更新后不再出现"自相矛盾" |
| 6 | 回答里出现不存在的引用编号（如 `[7]`，但只召回了 4 条） | 模型自由发挥 | 后端正则抽编号 + 校验存在性；前端再兜一层 | 点不存在的编号不会出错 |
| 7 | 上传大文件时接口直接 500 | 没限体积 | 限制 15 MB + 后缀白名单 + `Path(name).name` 防目录穿越 | 传错文件给明确提示 |
| 8 | 前端要等整段回答完才显示检索结果 | 先调检索再调生成，串行且不推送 | 先推 `meta`（检索结果）再逐 token 推 | 首屏等待从"等模型"变成"等检索"，感知快很多 |

## 六、可复现的命令清单

```bash
cd backend

# 1. 建库（改了 chunk 参数必须 --rebuild）
python -m scripts.ingest --rebuild

# 2. 建完立刻验一条检索

# 3. 只测检索（不花钱，秒级）
python -m scripts.eval --retrieval-only

# 4. 完整评测（要 Key）
python -m scripts.eval

# 5. 单元测试（含一条真实检索用例）
python -m pytest -q
```
